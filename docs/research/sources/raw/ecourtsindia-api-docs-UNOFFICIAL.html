Authentication

All API requests (except Court Structure) require Bearer token authentication. Include your API token in the Authorization header.

Bearer Token Format
Authorization: Bearer eci_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Prefix: eci_live_
Length: 41 characters
Format: Alphanumeric
Response Format

All successful responses follow this structure:

JSON
{
  "data": { ... },
  "meta": {
    "request_id": "req_abc123xyz"
  }
}

Security Warning

  • Keep your API token confidential. Do not expose it in client-side code.
  • Never commit tokens to version control or share in public repositories.
  • If compromised, contact us immediately to regenerate your token.

Core Concepts

Key concepts for working with the eCourts API.

CNR (Case Number Record)

A CNR is the unique 16-character identifier for every case in the eCourts system.

Pattern: [A-Z]{4}\d{12}
Components: [Court Code: 4 letters][Case Number: 6 digits][Filing Year: 4 digits]
DLHC010351552024 → Delhi HC, case 035155, filed 2024
HCBM050012342023 → Bombay HC (Kolhapur), case 001234, filed 2023
Court Hierarchy
text
Supreme Court of India (SC)
├── High Courts (37 across states/UTs)
│   ├── Original Jurisdiction
│   └── Appellate Jurisdiction
├── District Courts
├── National Company Law Tribunal (NCLT)
├── National Company Law Appellate Tribunal (NCLAT)
└── Specialized Tribunals
Cause List

A cause list is the daily schedule of cases to be heard in a specific courtroom. Each entry shows the case number, parties, assigned judge, expected hearing time, and case status. Use the Cause List Search endpoint to query schedules across courts.

Credit-Based Pricing

Most authenticated endpoints consume credits per request. Court structure endpoints and enum reference are free. Check your account balance and see the pricing page for details.

LegalCheck Jobs and Billing

LegalCheck is asynchronous. Submit once, save the returned data.code, poll its status_url, and fetch its report_url only after the job is completed. The resource code identifies the LegalCheck;meta.request_id identifies one HTTP request for support and diagnostics.

A newly accepted job costs ₹99 on PAYG or ₹33 with an active subscription. All status, report, list, and model reads are free. A terminal processing failure is refunded once to the original credit pools.

Each partner may have up to three jobs queued or running. Use a stable Idempotency-Key when retrying a submission so network retries cannot create another job or charge.

    GET/api/partner/search

    Case Search

    Deprecated soon

    Full-text search across 24Cr+ records with filters for party, advocate, judge, court, case type, dates, and faceted results.

    Deprecated soon. Case Search v1 keeps working and there is no shutdown date yet. New integrations should use Case Search v2; existing integrations should plan the move.

    ParameterTypeRequiredDescription
    querystringNoGeneral full-text search across all fields
    advocatesstring[]NoSearch by advocate name. Repeat the key for multiple values; values are OR’d, and within each value all tokens must matche.g. advocates=Rahul Sharma&advocates=Amit Patel
    judgesstring[]NoSearch by judge name. Multiple values are OR’d
    petitionersstring[]NoSearch by petitioner name. Multiple values are OR’d
    respondentsstring[]NoSearch by respondent name. Multiple values are OR’d
    litigantsstring[]NoSearch both petitioners and respondents. Multiple values are OR’d (find cases involving any of the listed people)e.g. litigants=Ramesh Kumar&litigants=Suresh Singh
    nameMatchModestringNoHow tokens inside each name value must match: all (default, every token), any, phrase, fuzzy (edit distance 1 per token). Applies to litigants, petitioners, respondents, advocates, judgese.g. nameMatchMode=fuzzy
    actsAndSectionsstringNoFree-text search of the acts and sections string the court wrote. A hit still returns that string as actsAndSections, not the structured provisions array (that is on Case Detail)e.g. actsAndSections=IPC 420
    actKeysstring[]NoExact India Code act keys. A case matches if it cites any of them. Repeat the keye.g. actKeys=1860/45&actKeys=2023/45
    provisionsstring[]NoExact section references, act key, unit and number joined by |. A case matches any of them. This does not match a parent act or a neighbouring sectione.g. provisions=1860/45|s|420
    provisionPathsstring[]NoAct, section or sub-section paths. An act path (2023/45) matches every section of that act; a section path matches that section and its sub-sections. A path is an act key, or an act key with unit s, a or o and a number, or unit r with order/rule (1908/5|r|7/11). Anything else is dropped. At most 50 valid paths are usede.g. provisionPaths=1860/45|s|420&provisionPaths=2023/45
    provisionFacetPrefixstringNoWhich level the provisionPath facet counts. Omit it to count acts. An act key counts that act’s sections; a section path counts its sub-sections. Applied only together with at least one valid provisionPaths valuee.g. provisionPaths=1860/45&provisionFacetPrefix=1860/45

    Important: Search results do not include a "case title" field. Construct a display title using petitioners/respondents arrays (e.g., "ABC Ltd vs XYZ Corp").
    Array parameters are passed by repeating the key (litigants=A&litigants=B). A comma inside one value is part of that value, not a separator. Each result’s actsAndSections is the court string. Structured citations, with India Code links, are on Case Detail as courtCaseData.provisions. The provisionPath facet counts acts, or the children of provisionFacetPrefix, and is left out of an unfiltered browse.

    Moving from v1

    1. Change the URL to /api/partner/v2/search.
    2. Keep your parameters as they are.
    3. Read data.facetMode on every response.
    4. If it is counted, use facets as before.
    5. If it is full, facets is {}. To get counts, narrow the search with a filter, or, for a text or name search, sort by a date field (for example sortBy=filingDate desc). A date sort drops relevance order in exchange for an exact count.
    6. Use Facet Catalog: Search to turn a name, such as a district, into the exact filter value.

    Important Notes & Gotchas

    Common pitfalls and things to watch out for when using the API.

    LegalCheck Full Verbosity Is Still Partner-Safe

    verbosity=full increases the amount of allowlisted case detail; it does not expose private engine inputs, model processing material, or internal search data. Treat the report's limitations and disclaimer as part of the result.

    Wrong Enum Codes = Silent Empty Results

    If you pass wrong enum codes to search, you get 0 results with no error. Always verify codes using the Enum Reference endpoint or the enum tables below before searching.

    cURL
    # WRONG — returns 0 results silently
GET /api/partner/search?caseTypes=BAIL_APP

# CORRECT — use validated code
GET /api/partner/search?caseTypes=BA

    Order AI Analysis is On-Demand (10-60s)

    The order-ai endpoint performs on-demand processing from government court servers on first access. Expect 10-60 second latency. If aiAnalysis is null, retry up to 3 times with 15-30s waits. Fall back to order-md for raw text if needed.

    Order Markdown Can Take Up to 300 Seconds

    The PDF conversion pipeline is slow. Full order text is already available in Case Detail response under files[].markdownContent. Only use the order-md endpoint when you need the watermarked PDF for official submission.

    High Court Codes Need Bench Suffix

    High Court codes must include bench suffix for searching. DLHC returns 0 results — use DLHC01.

    cURL
    # WRONG — base code, returns 0 results
GET /api/partner/search?courtCodes=DLHC

# CORRECT — full code with bench suffix
GET /api/partner/search?courtCodes=DLHC01

    NCLT Codes Need Trailing '0'

    NCLT bench codes must end with 0 for searching.

    cURL
    # WRONG: GET /api/partner/search?courtCodes=NCLTDL
# CORRECT:
GET /api/partner/search?courtCodes=NCLTDL0

    SC = India (Supreme Court)

    In state codes, SC represents the Supreme Court of India, not a state. It appears in the states list as "state": "SC", "stateName": "India".

    Cause List Uses Offset Pagination

    Cause list search uses offset-based pagination, not page numbers. To get page 2 with limit=20: offset=20. Next page: offset = previous_offset + limit.

    courtNo vs court in Cause Lists

    In cause list results, courtNo is the room number and court is the internal identifier. These are different fields — don't confuse them when filtering.

    All Dates Use YYYY-MM-DD Format

    All date parameters and response fields use YYYY-MM-DD format. Datetime fields include timezone suffix (Z).

    Case Category is Free-Form in Case Data

    Case category enum codes are search filters only. The actual caseCategory field in case data is free-form court text (e.g., "Constitutional Writ"), not a value from the enum.

    Acts/Sections Filter — Exact Match, Very Limited Coverage

    The actsAndSections filter requires the exact stored-text format and has very limited index coverage. Most cases do NOT have this field populated. The filter also doesn't appear in activeFilters.

    cURL
    # WRONG — abbreviation, returns 0:
GET /api/partner/search?actsAndSections=IPC+302

# TECHNICALLY CORRECT format — but still returns 0 for most courts:
GET /api/partner/search?actsAndSections=INDIAN+PENAL+CODE+-+302

# RECOMMENDED — use full-text query instead (432K+ results):
GET /api/partner/search?query=IPC+302

    For general act/section searching, use the query parameter instead. The actsAndSections filter is only reliable when you know the exact stored text format and the case has this field populated.

    Refresh is Idempotent Within 15 Seconds

    Calling refresh multiple times within 15 seconds is safe — no duplicates are created. Wait 5-10 seconds after queuing before fetching updated case details.

    Best Practices

    • Cache responses: Store case details locally to reduce API calls and costs.
    • Batch operations: Use search to find multiple cases instead of individual lookups.
    • Handle rate limits: Implement exponential backoff for 429 responses.
    • Use refresh sparingly: Only request case refresh when you need the latest data.
    • Store request IDs: Log request_id from responses for support inquiries.
    • Make LegalCheck retries idempotent: reuse the same Idempotency-Key with the same body after a timeout or connection failure.
    • Honor asynchronous state: poll the LegalCheck status URL using Retry-After and fetch a report only after completion.
